# Benchmarking models

A benchmark here buys one decision — which model, effort, tier or harness a call site runs on, anywhere in the repository: a product agent's role, a classification step in the ingestion pipeline, a backend writer, a GitHub Actions agent workflow, the model a coding agent or review bot runs on — at the price of hours of wall time, shared quota and real dollars. The rules are about the measurement, not any one suite. The skill exists because the same comparisons were re-run across sessions with their results left in chat, and because most wasted rounds came from a handful of harness traps, not from the models.

## Before designing anything, read what is already known

1. `docs/benchmarks/README.md` — the ledger: every benchmark run so far (setup, result, cost, where the raw data is), the standing facts (quota, prices, cache behavior, measured workload shapes) and the instruments that exist. A question the ledger already answers is not re-measured; a partial or aborted entry is a hypothesis to sharpen, not a blank.
2. Public benchmarks for the same task class — agentic tool use, text-to-query, instruction following, long-context — and the vendor's own guidance for the model and its effort levels. Extrapolate to the call site's own workload shape — prompt length and how much of it is a stable prefix, output length, tool steps per task, how the output is judged (a row diff, a rubric, a compile, a human) — to write a hypothesis: which arms can plausibly win, which are settled by prior results, which public gap is so wide that a brief validation is enough. Arms get cut this way before anything is spent. Pull public benchmarks live every time and keep their figures out of the ledger: leaderboards move with every model release and rescoring, so a persisted score would be read as current when it is not. An entry names which public sources were consulted and the hypothesis they produced, never their numbers.
3. The design doc, config or workflow file that owns the call site's current pick, and why it was picked, with any reopen trigger already written down (for a workflow, its `model:` line and the PR that set it; for the model gateway's lanes and caps, the doc that owns them).

**Candidates for a model the deployed product calls** come only from the providers the company approved for customer data (`AGENTS.md`, Customer data and processors), and a standing decision about which model families are in or out of that pool is recorded in the model-selection doc. Coding agents and review bots are outside this pool. List what the provider's catalog offers with a read-only identity and ask the user to deploy what is missing. When a call regresses on a successor model, fix the call (a prompt budget, an instruction) before proposing to keep it on the old generation; pins already recorded with their reason stand.

Test the hypothesis, not the space. The cartesian product of models × efforts × tiers × harnesses is not a design: pin every lever but the one the decision turns on, and add a second lever only where prior results say it interacts. Measured on one agentic eval suite, effort changed one model's net pass count by only a few percent of cases while two effort levels of one model disagreed on several times as many individual cases (so a paired test is sized on discordant pairs, not on the net gap), and the maximum effort scored at or below the next level down on every model tried while doubling median latency, so effort is rarely the arm worth paying for on agentic workloads; a call site with a different shape re-checks that with one arm, not four. The goal is a Pareto front on quality, latency and cost, not the top score.

## Estimate, then ask

Before the first paid call, give the user one estimate and wait for their go. It carries:

- **Arms and cases** and what each arm is expected to show.
- **Dollars**: cases × arms × tokens per case at the arm's price, with the cached share priced at the cache-read rate (most eval and chat input is cache reads; the ledger's workload-shape section has the measured shares and per-case and per-run figures for each model). Price from the official pricing page read that day, never from memory, from a catalog constant or from the ledger's price table (a dated snapshot that exists to interpret past entries, not to design new runs): a model catalog has carried a price 5× over list, and an SDK's cache-write counter has read several times the billed amount.
- **External services**: anything else the arm calls — a browser vendor, its proxies, a sandbox, a GPU host, a data API — bills on its own meters (proxy gigabytes, session minutes, concurrency tiers), and these can cost more than the models. Quote each meter's price, read on the vendor's pricing page for the plan the account is actually on, times the expected usage per run from the ledger or the vendor's docs, labeled unmeasured.
- **Wall time**: cases × median seconds per case ÷ threads, bounded by the deployment's rate cap (below), plus the runs that will fail and be repaired. Serial arms add up; say so.
- **Quota**: which resource and deployment, at what thread count, and whether anything else is sharing its cap right now.
- **Data and where it goes**: which instrument's payloads the arm sends and to which vendor and location. Eval suites and replayed production conversations carry customer data (the ledger's instruments table marks which). A benchmark is internal work, so a service on the internal-work list (`AGENTS.md`, Customer data and processors) may receive it. Any other service the arm calls (a model, a browser vendor or its proxies, a sandbox, a GPU host, another product of a listed vendor, one tried earlier on a trial key) gets customer data only with the user's go, so name it here, or run that arm on a customer-data-free instrument (synthetic cases, a demo account).
- **The stop rule, declared now**: the sample size, or the sequential boundaries — one for success and one for futility — at which a partial result counts as final. Deciding it after peeking at intermediate results inflates the false-positive rate and voids the paired test.

The user decides whether the answer is worth the wait and the spend; an estimate that turns out wrong by more than about 2× is reported as soon as it is known, and the run pauses if the money side moved.

**A small probe is not a benchmark.** A handful of calls that finish in about a minute and cost about a dollar or less — a time-to-first-token probe, a canary case, checking that a deployment answers, a cache-warmth check — skips the estimate, the polling and the ledger entry: the overhead would cost more than the probe. Three things still hold for it: it never touches the production key; a probe to any other service sends synthetic payloads only, since the probe skips the estimate where the user would see the vendor; and if its reading ends up deciding something, the reading goes into the ledger or the design doc so it is not re-measured.

## Make the instrument fair before trusting it

- **The harness is an arm too.** The same model scores differently under your own agent loop, a vendor's CLI agent, a native API and an OpenAI-compatible shim: provider-executed tools exist only on some API kinds, a short context window overflows one large tool result, a compatible vendor may not serve the newer API shape. Decide which harness the decision is about and hold it fixed, or make it the lever. A remotely dispatched eval answers with the deployed image and context while a local arm answers with the branch's, so the two are different harnesses: never mix a dispatched arm with local arms in one comparison.
- **Fixed judge, fixed grader, across every arm.** Whatever scores the output — a verifier model and judge, a rubric model, a compile step, a human reader — is an instrument; changing it mid-study invalidates the comparison. Know the instrument's bias: a suite or rubric tuned on one model measures fit to the product as tuned, not raw capability. Say that in the write-up.
- **The grader must not measure its own error.** Facts read from moving tables hours after a run, criteria that demand full listings, and a judge blocked by the provider's safety filter all show up as model deficits. Grade after all arms finish, bound counts to the run's period, tolerate a few percent, and read the judge's raw response before blaming an arm.
- **Noise floor first.** Measure it before reading a gap: every instrument flips some cases between two identical runs (the ledger records each instrument's floor), and a new instrument gets its floor from two identical runs before its first comparison. A gap under the floor needs repeats: compare arms on shared pairs with a sign test or McNemar, never on per-arm percentages, and re-run only the cases where arms disagreed. Spot checks lie: a 10-case look that went from 0/10 to 3/10, and an 8-case look at a higher effort, both vanished at full scale. Settle close arms on the full paired set or not at all.
- **Pin experiment knobs where a run cannot lose them, and check the knob reaches the model.** A stored reasoning effort can be dropped silently when the request carries none, a test runner may send none, and some models accept only a subset of levels — on any other the level is the deployment's default and nothing records it. The answer's recorded effort is the request's level or the catalog's, never what a downstream proxy rewrote, so a proxy arm is verified from the proxy's own log. Config files read per request let a mid-run revert silently downgrade an arm, and any edit to the system under test mid-run invalidates the measurement: commit before starting arms and set knobs in the launcher or the proxy.
- **Local baselines are only baselines once their tool errors are read.** A missing environment variable, a stale key, or a transport error look exactly like agent failures and can reverse an A/B conclusion. Check each tool call's error and the error split (failed on error vs on asserts) before reading a pass rate.
- **Latency is measured per workload shape, unbuffered.** Time to first token depends on prompt length and effort more than on model (one model can win one shape and lose the other). Probe the shapes the call site actually sends, read streamed frames unbuffered (iterating a response line by line can batch 8 KB and add seconds), and measure provider-side stalls on the provider's own metrics before attributing them to a model.

## Caching decides the bill and the order

Prompt caches are commonly per deployment: a prefix served by one deployment is cold on another and stays warm on the first after you leave; a hit needs an identical prefix, and a cache write can cost more than an uncached read, so a churning prefix costs more than no cache (the ledger's cache section has the measured warmth, the documented lifetimes and the rates). Consequences for design:

- Run an arm's cases back to back on one deployment so the shared prefix is written once; interleaving arms across deployments costs nothing extra, interleaving prefixes on one deployment does.
- Keep the system prompt and tool definitions byte-identical across cases of one arm; put the varying part last.
- Report the cached share per arm from the usage's cached-token and cache-write counts: a cold-start slice reads a fraction of what the run reads, and a per-arm cost quoted without its cache share is not comparable.
- Price a cross-vendor arm on its own cache rules and tier multipliers, read live from its pricing page (the ledger's price snapshot lists the shapes to look for: write and read multipliers, regional and priority factors).

## Quota and parallelism

Internal benchmarks run on the internal lane's resource and key, never on production's (`AGENTS.md`, Deployment & Infrastructure Safety). The deployment's capacity is a rate cap the provider enforces; raising it is the user's decision, not a benchmark's.

Design parallelism from the cap and the arm's peak minute, not from CPU (the ledger keeps each instrument's measured peak minute and how many threads fit each cap). Client SDKs that honor `retry-after` slow down a run slightly over cap; a run well over it collapses (a 2-thread suite lost half its cases while a sibling worktree shared the cap; a vendor key with a sliding window lost most of its calls at two threads). The whole cap may be used, but it is shared with staging, CI evals and every other worktree on the machine: look for other runs first, and read the provider's rate-limit headers before blaming the cap, since providers lower effective limits under load. A retry proxy with a 20 s backoff absorbs the residual 429s and doubles as the cache-share meter.

Instrument-specific constraints outrank quota, and each instrument's list lives in its row of the ledger's instruments table (for example: arms one after another, one dispatch at a time).

## While it runs

A run longer than five minutes is polled, not awaited: read its progress every few minutes and keep a running estimate of where the arm will land. Know what the instrument leaves behind mid-run: a runner that writes results only after every case finishes is either run in batches that each leave a file, or read from its run log, and an arm stopped early keeps only that log. When an arm calls an external service, read each of its meters (the vendor's usage or billing dashboard) after the first run and before the second, under the 2× rule of the estimate. Stop the run when the conclusion is already final by the stop rule declared in the estimate — the success or futility boundary is reached — or when an arm is failing on infrastructure rather than behavior, and record the partial result as such, with the rule it was stopped under. A running estimate of where an arm will land is for planning the next arm, not a reason to stop this one. A run nobody will read to the end is money spent on nothing; sessions have been ended with "give me the numbers you have, don't run new evals".

Repair, do not restart: re-run only the cases that errored on infrastructure (one thread), merge the passes, and tell infra errors apart from asserts in the write-up.

## Persist the result, not the code

Every benchmark, finished, stopped or aborted, gets an entry in `docs/benchmarks/` in the shape the README gives, in the same PR as any decision it changed. It carries the question, the arms and their pinned levers, the instrument and its known bias, the numbers per arm (quality, latency, cost, cache share, cases and repeats), the paired comparison, the wall time and dollars spent against the estimate, and a pointer to the raw per-case results — a compact CSV in the entry or a committed artifact, because a matrix whose files were deleted survives only by luck in some PR's head commit. Whether the code is kept is the session owner's call; a script that is kept follows the experimental-folder convention in `AGENTS.md`.

A decision the benchmark changes is written where the call site's pick lives — a design doc's table, a config value, a workflow's `model:` line, with a one-line why — as current truth; the entry keeps the history. A latency gap against the current pick is a verdict in the entry, accepted (with why) or blocks, never "unexplained": a gap left unexplained is a decision nobody made, and the next step ships it. For a product agent's model change, the PR carries that verdict. The decision itself is the user's: present the Pareto front with each arm's quality, latency and cost, name the instrument's bias and what was not tested, and recommend only where the gap clears the noise.
