# design-review

**What.** Reviews a design doc at any stage of its lifecycle, with two jobs in this order: find what the analysis missed (dragons, unstated assumptions, missing whys), then cut the doc down to the result.

**Why.** Design docs rot in two directions: they miss the reason behind a non-obvious shape, so a future change breaks it, and they accumulate analysis, history and implementation detail that the code already shows, so nobody reads them and agents load stale context. The review reads the doc next to the code and simulates a fresh session holding only both. It auto-fixes what is safe to cut (vague language, history framing, code-mirroring prose, collapsed analysis behind decided decisions, stale state), lists every cut so the user can veto, carries forward any embedded why or dragon, and asks before removing a why the code does not show or touching a decision. After two passes it recommends stopping.

**How it fits.** Follows `/design`, uses the same tests ("What Goes in the Doc" in [`design`](../design/SKILL.md)), and advances the doc's status, deleting the State section at launch.

**Wire up.** Nothing beyond the design-docs folder.

**Origin.** Adapted from the `document-review` skill in [EveryInc/compound-engineering-plugin](https://github.com/EveryInc/compound-engineering-plugin) (MIT, Copyright (c) 2025 Every; [license text](../../licenses/MIT-every-compound-engineering-plugin.txt)). That skill refined brainstorm and plan documents with six steps (get the document, assess, evaluate against a criteria table, name the critical improvement, make changes, offer the next action), its iteration guidance and its "What NOT to do" list; this one keeps that skeleton. The author's changes: it reviews design docs against the code they describe instead of a document alone; it adds the second job of cutting the doc down to the result, with the code, breakage and resume tests from `/design`; it probes for dragons, inherited decisions and design category; it replaces the four criteria with its own table (result not process, complements the code, one owner per subject, load-bearing whys, decision provenance, dragon quality, current state, category fit, open-option quality, no effort estimates, timelessness, alongside clarity, specificity and YAGNI); it sets which cuts are auto-fixed and which need approval, carrying forward any why or dragon; and it can advance the doc's status.
