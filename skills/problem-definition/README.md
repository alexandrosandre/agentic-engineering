# problem-definition

**What.** Helps state the problem before anyone picks a solution: the current framing, the struggling moment, the problem separated from the requested feature, and whether the problem matters to whom.

**Why.** A problem stated as a feature locks in one answer before the need behind it is understood, and new technology invites working backward from a tool to a use. The skill keeps to four moves and a few questions that usually unstick a conversation ("What is the user doing right before they hit this?", "What do people do today to work around it?"), flags the usual traps, and grounds claims about users in their real sessions (`read-user-sessions`) instead of assumed behavior. When the framing stays abstract, a throwaway prototype the user can react to is often the fastest way forward.

**How it fits.** Upstream of `/design` and `/prototype`; `/prototype` uses only its want-versus-method separation.

**Wire up.** Nothing.
