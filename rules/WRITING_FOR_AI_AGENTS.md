# Writing for AI agents

Read this before writing or editing text an AI reads as instructions: any `AGENTS.md`, the agent skills, subagent definitions, and system prompts in code. Prose written for a model is not documentation for humans: every always-on line is re-sent on every step of every turn and competes for the model's attention with the user's actual question.

- **Fewest high-signal tokens.** Trimming is a quality lever, not only a cost one: compliance falls with the number of rules that must hold at once (one 2026 study: all of 10 rules kept in 94% of answers, all of 40 in 24%), and every added line is a behavior change to test: a single length-cap line in one coding agent's system prompt cost 3%, found when its vendor removed lines one at a time. What goes is text that does not change behavior: repeated statements, process the model already follows reliably, style lines and examples whose removal changes nothing. What stays is what only the author can supply: the outcome and how success is judged, the required output shape, stopping and permission constraints, tool-routing rules, the facts about the product and environment the model cannot see, and the reason behind each rule. Before adding, ask what it prevents; before keeping, ask whether removing it would cause a mistake.
- **State it once, in one home; cross-reference instead of restating.** Duplication dilutes and contradictions are worse — this model generation burns reasoning reconciling them. A rule that needs an exception states the exception where the rule lives.
- **Right altitude: the heuristic plus its reason**, not an if-else recipe and not a vibe. Given the why, models generalize to the cases you did not enumerate, which is what keeps the list short.
- **Test the mechanism you give as the reason.** Models generalize from the *why*, so a wrong one misfires everywhere the rule reaches and the next rule that cites it inherits the error as fact. Verify before writing, and name the evidence in the line so the next reader need not re-derive it.
- **Don't inflate emphasis.** Reserve ALWAYS, NEVER, MUST and caps for true invariants — safety, permissions, required fields, actions that must never happen — and give a judgment call a decision rule with its reason instead. Spread wider, they stop marking priority, and current frontier models over-trigger on them: wording made forceful so a tool or skill would fire now makes it fire where it should not (the model vendors' own prompting guides say so). Delete emphasis added to carry older models.
- **No scaffolding of how to think** — step-by-step procedures degrade output on models that already plan. State the goal, the constraints, the output contract, and the specific check the result must pass (a test, an eval, a render); keep numbered steps only where the order itself is the requirement. Generic deliberation ("consider every possibility", "re-verify until certain") multiplies tokens with no measured gain, while a check that names one specific rule works. Never ask the model to write out its reasoning in its reply, which current models may refuse; ask for a short explanation or a summary of the actions taken.
- **Current truth only.** Describe the present as if it had always held: no prior behavior, no migrations, no transition windows or date-gated caveats. The model treats any stated past as live casuistics — it hedges answers against eras and carries "before X / after X" branches the repo has already left behind. This holds even while data written under an old behavior still exists: teach the new truth and let the old data age out. History and the reasoning behind a change live where agents don't read — design docs and chat.
- **Examples: few, canonical, current.** First to cut when trimming; a stale one is actively harmful because models copy its details. Where evals exist, keep only examples whose removal regresses one.
- **Progressive disclosure.** Always-on carries what is needed *before* any tool call: identity, rails, and the index saying where the rest lives. Depth sits where the harness loads it when it applies: a directory's rules in its `AGENTS.md` (behind a one-line shim for agents that need one), which the agent attaches when a file there is read inside the session's working directory; a procedure in a skill behind a trigger-rich description. An explicit read protocol ("before doing X, read Y") is the fallback, followed in about half of the cases where it was the only route in the sessions measured; "the docs are available" gets skipped. A skill's must-hold lines go in its first few thousand tokens, which is all some harnesses re-attach after compaction.
- **A tool description is the tool's contract**: what it does, when to use it and when not, what each parameter means, the return fields that matter, and how it fails — precise, and stated there once. Steering, worked examples and a system prompt restating the contract are the bloat; a missing return field or failure mode is the gap.
- **A delegation brief carries the constraints the subagent needs, verbatim.** Constraints are lost mostly where the lead restates the task, and some built-in subagent types start without the repository's rule files. A limit that must hold belongs in the subagent's tools or a check.
- **Prefer mechanism over prose** for anything that must always happen: a validator, hook, or CI check guarantees it; prose only advises. Delivering a rule does not make it hold: most rules agents broke were in context when they broke them, so a rule that keeps breaking needs a check where it applies, not more or louder text.
- **Caching is not a licence for bulk.** Cached tokens still bill against rate limits and still occupy attention.
- **Deleting is maintenance.** Remove rules the model already follows, workarounds for superseded models, and duplicated statements. Add a rule learned from a coding-agent correction only once its failure has repeated or was costly; a rule for a failure the reading model's own vendor guide documents can go in before it happens here, and a one-off fix to a product agent's answer is gated by its eval instead. Judge a change on the same cases with and without it, counting the failure it targets: rewording alone reshuffles which cases pass far more than reruns do, and about ten cases can show only a very large effect. Change a working prompt in small steps and, where an eval exists, run it after each: a whole stack rewritten at once leaves a regression with no cause to point at, and a cut that regresses comes back in its shortest form. Re-read the whole file afterwards, so what you added cannot contradict what was there.

Distilled in 2026 and re-vetted against the frontier labs' current prompt and context-engineering guidance and against measurements of real agent sessions, screened to sources under about twelve months old; every rule above held for the vendors checked. That screen is part of the rule: pre-frontier advice inverts several of these (more few-shot is better, CAPS to make rules stick, repeat instructions at top and bottom). Where current vendor guidance diverges — narration between tool calls, blanket brevity instructions, generic "double-check your work" prompts, how readily to delegate — tune for the model that reads the text, from its vendor's own guide. Re-vet when the model generation turns over, and drop stale findings rather than accumulating them.
